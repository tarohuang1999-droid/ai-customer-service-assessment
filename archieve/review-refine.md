## 1. 對這份 review 的理解

你希望答案能交代一個實際可推進的方案：

- **先對齊需求，再分階段開放功能。**每階段有交付內容、部門依賴、驗收及 rollback 條件。
- **具體到能討論實作，但不擴大 PoC。**知識查詢、訂單查詢、草稿與寄信的邊界要清楚，不需要把正式系統全部做出來。
- **AI 輔助與人工負責可以同時存在。**轉人工不必等於禁止摘要或草稿；是否自動寄出是另一個決策。
- **指標要能支持決策。**哪些是安全底線、哪些判斷品質、哪些衡量效益，不能全部塞進一個正確率。
- **文字精簡，必要細節不能省。**少用方案代號、抽象提醒與重複敘述，多寫條件、操作、負責人和結果。

原答案的主要問題是：項目雖然有列到，但部分內容不足以拿來對齊需求或執行；同時又放了很多缺乏依據的門檻，造成篇幅長卻不夠具體。

## 3. 共通前提：部署、系統與權限

### 3.1 Local LLM 與資料使用

**你的意思：**沒有簽約供應商，涉及訂單與客戶資料時，先在內部跑模型；每天 350–700 件應有機會負擔。

- **Agree：**內部部署是值得評估的路徑，也應避免把「等待外部供應商」當成唯一推進方式。
- **Disagree：**題目限制的是未經評估與簽約的外部服務，不能直接推導成「只能 local LLM」。也可以先做虛構資料 PoC、公開知識查詢，並行處理供應商評估。內部部署本身仍需取得核准。
- **保留：**每日件數不足以證明模型容量夠用。還需看硬體、模型、工單長度、每單呼叫次數、尖峰與可接受等待時間。

**可選修改：**將 local LLM 列為部署候選；以實際工單長度與尖峰批次做小規模測試，再決定。權限、log、模型追蹤、備份及外部監測服務都納入資料流，不能只確認模型在哪裡跑。

### 3.2 跨系統、低 QPS 與「審核」

**你的意思：**現況中最重要的整合限制沒有被展開，無法判斷方案能否落地。

- **Agree：**應先確認另外兩三個系統是什麼、查哪些欄位、由誰維護，以及是否有可用介面。不能自行假設一定是付款、CRM 或出團系統。
- **補充：**題目的「申請權限、走審核」指訂單 API 的存取申請流程；不等於每次唯讀查詢都需要主管簽核。退款超過 30,000 元是另一個業務簽核流程。
- **保留：**日均件數少不代表低 QPS 沒影響。單筆多次查詢、批次進件、重試與其他系統共用配額都可能造成限流。

**可選修改：**先確認 QPS 數值、共用範圍與尖峰；初期限制併發、排隊並限制重試。等待過久就交由客服查詢，不讓模型反覆呼叫。快取只用在允許過期且已完成權限檢查的資料。

### 3.3 MCP server、服務帳號與資安

**你的意思：**將知識查詢和訂單查詢分開提供給 agent，申請正式的服務身分；初期不提供訂單修改。

- **Agree：**兩類能力應有獨立工具範圍與權限。訂單先唯讀、寄信另外授權，容易說明，也容易停用。
- **Disagree：**能力分開不代表一定要部署兩個獨立 MCP server。可先使用同一服務中的獨立工具與權限；是否拆服務取決於維護責任與隔離需求。
- **補充：**「申請 user」應明確寫成專用服務帳號或服務身分。模型不持有任意憑證；工具端驗證客服權限及客戶與訂單的關聯，不能因為 agent 有帳號就查所有訂單。

**可選修改：**架構圖畫出「知識查詢工具」「訂單唯讀工具」「寄信工具」，註明可透過 MCP 提供。正式系統保留這個方向，PoC 不必實作 MCP。權限申請、最小權限、憑證管理、資料回傳範圍與稽核放在同一處說明。

## 4. Q1／Q3：以推進計畫串起方案

**你的意思：**不要一直寫「用 C 驗證 B」，應直接說明先完成什麼，再開放哪些能力。

**Agree：**採用以下五階段；Q1 說明選擇與順序，Q3 展開實作依賴和流程，避免兩題重複。

| 階段 | 要完成的內容 | 部門依賴 | 可以開放什麼 |
| --- | --- | --- | --- |
| 1. 資料與權限準備 | 釐清知識版本、模板、instruction、分類與 eval；盤點資料流和 API | 客服確認內容；資訊提供介面；法務／資安核准資料用途 | 離線驗證，不接真實自動寄信 |
| 2. 知識查詢與客服輔助 | Agent 查知識、加分類與 priority、產生草稿；記錄 monitor 與 feedback | 試點客服參與核對，知識負責人修正內容 | 查詢、摘要與人工確認的草稿 |
| 3. 訂單查詢與寄信整合 | 加入唯讀訂單工具，完成身分核對、限流；串接寄信能力 | API 權限、訂單資料負責人、工單系統窗口 | 訂單查詢後草擬；寄信仍需人工確認 |
| 4. 低風險自動寄信 | 訂出允許情境、排除條件、驗收與停用開關 | 客服主管驗收，資訊確認寄送及回退機制 | 僅符合條件的工單自動寄出 |
| 5. 持續評估與改善 | 抽查、事故回歸、更新知識與 eval，檢查新問題類型 | 客服與系統負責人定期 review | 有證據才擴大適用範圍 |

**保留與調整：**

- 第五階段是持續工作，監控與 feedback 從第二階段就開始，不能等自動寄信後才做。
- 第三階段「做好寄信介面」不等於「授權 agent 自動寄信」。寄送前仍要檢查工單狀態與核准紀錄。
- Q3 題目明確要求 workflow 與資料流；implementation plan 可以補充，但不能取代設計圖。
- 每階段要有進入條件、交付與驗收人，不必在資訊不足時硬排完成日期。跨部門窗口確認後再排期。

**去重應改成具體例子：**工單系統可能重送同一個 webhook，系統辨識已處理事件，避免產生重複草稿或重複寄信。客戶在同一工單補充新內容仍要處理，不能只用 ticket_id 把後續訊息全部忽略。

## 5. Q2：重寫成六項完整的需求定義

### 5.1 目標與驗收

**Agree：**不能用一個「省時 20%」代表所有階段。數字不是不能提出，而是必須標明基準、適用情境、量測方式及誰確認。

- 資料準備：試點文件均有有效版本及負責人，eval 有標註與例外案例。
- 草稿輔助：先看正確性與客服修改負擔，再看處理時間改善。
- 訂單查詢：確認查詢授權正確、結果可追溯，且限流時能回退。
- 自動寄信：提高安全要求，並追蹤錯答送出、客訴與重新接手。

**可選修改：**保留少量、可解釋的初始門檻，例如未授權訂單查詢與重複寄信不得發生；效率目標先取得人工基準，再與主管確認。Q2 放驗收摘要，公式與門檻集中在 Q4。

### 5.2 使用者、正常情境與例外

**Agree：**一行「客服看草稿」不夠。至少需要覆蓋：

- 客服：一般產品詢問、訂單查詢、缺資料、多重需求、退改／投訴、來源衝突、系統失敗。
- 主管：退款簽核、重大客訴、品質異常、暫停或恢復功能。
- 知識維護人員：文件更新、版本衝突與失效內容下架。
- 資訊／資安窗口：權限申請、服務異常與存取稽核。

**保留：**不必窮舉所有 edge case。選會改變分流、權限或回覆行為的例外，寫成「情境 → 系統協助 → 人工責任」。

### 5.3 輸入輸出與前置條件

**Agree：**按系統或能力分類，比把所有欄位塞在一行清楚。

| 能力 | 輸入 | 輸出／邊界 |
| --- | --- | --- |
| 工單接收與分類 | 工單欄位、事件／訊息識別、既有狀態 | category、priority、route、reason；多重需求可加標籤 |
| 知識檢索與草擬 | 問題、允許存取的文件、模板與 instruction | 草稿、引用來源、待補資訊與風險提示 |
| 訂單查詢 | 經核對的客戶與訂單關聯、授權查詢參數 | 最小必要的訂單資料、查詢時間或失敗原因；不修改訂單 |
| 寄送與回饋 | 已核准的草稿或符合自動寄送條件的回覆 | 寄送狀態、審核／規則紀錄、客服評分及修改原因 |

**前置條件應分階段：**沒有訂單 API 權限會阻擋訂單整合，但不必阻擋虛構資料 PoC 或經核准的知識試點；沒有資料處理核准則不能把真實工單接入該環境。

### 5.4 五個關鍵問題

依你的 review，可改成以下五組；具體系統資訊放在每組追問，不另外擴成十幾題。

| 關鍵問題 | 要排除的風險 |
| --- | --- |
| 各部門最需要解決哪些需求？優先順序與第一階段範圍是什麼？ | 做出功能卻沒有改善主要問題，或範圍持續擴大 |
| 每項需求目前的表現、最低驗收值與驗收人是誰？ | 大家對「有幫助」「夠準」的定義不同 |
| 最不能發生哪些情況？發生時誰能停用、回退與對外處理？ | 高風險行為沒有限制，事故發生時無人決策 |
| 各部門窗口、知識／資料負責人與權限核准人是誰？ | 文件、跨系統查詢及資安條件無法落地 |
| 權限、資料、開發及客服試用各需多久？何時 review、驗收與決定下一階段？ | 只排工程時間，忽略審核與客服參與成本 |

## 6. 分流、草稿與自動寄送應分開

**你的意思：**即使最終必須人工處理，AI 還是可能提供摘要、模板或草稿；此外要有 category 與 priority，而不只有 auto／human。

- **Agree：**分類是客戶問什麼，priority 是處理急迫性，route 是由誰承擔後續處理；是否可草擬、是否可寄出是不同決策。人工接手不必失去全部 AI 輔助。
- **Disagree：**不能保證 AI 對任何信都能產生有用草稿。資料衝突、查詢失敗或高風險承諾時，可能只適合摘要、待確認事項或收件模板，不能假裝已有實質答案。
- **保留：**低信心可作為需覆核的訊號，不宜直接變成業務分類，也不能只靠模型自評數字決定是否寄信。

**可選修改：**PoC 保留題目必填的 ticket_id、category、route、reason，加 priority 即可。route=human 時可另附有限的輔助資訊；route=auto 在 PoC 明確定義為可自動草擬，不等於可寄送。正式系統再以獨立條件控制寄信，避免為了描述完整性而增加過多欄位。

## 7. Q4：監控、評估與流量要對得起來

### 7.1 指標分層

**Agree：**需要知道哪些指標觸發停用、哪些幫助優化，以及誰看、多久看一次。

| 層級 | 主要指標 | 對應決策 |
| --- | --- | --- |
| 安全與客戶影響 | 個資／越權、錯誤交易承諾、重複寄送、AI 相關客訴 | 立即處置，必要時停用受影響能力 |
| 回覆品質 | 分類錯誤、事實錯誤、漏答、引用不符、語氣問題 | 按類別與嚴重度修正；不能只看平均正確率 |
| 使用效益 | 客服草稿評分、重寫比例、人工處理時間、接手率、任務成功率 | 決定保留哪些能力、是否值得擴量 |
| 系統健康 | 系統 error rate、工具失敗／限流、生成時間與待辦積壓 | 告警、降級與容量調整 |

**可選修改：**用一張精簡監控表列「分子／分母、來源、初始門檻、負責人、觸發動作」。初期可利用工單與應用 log 產生日報，不必另外建監控平台。

### 7.2 客服評分、latency 與 judge

- **客服評分：Agree，但要避免增加操作負擔。**試點可要求審核後單擊評分：5＝可直接使用、4＝小幅潤飾、3＝需補充、2＝大幅重寫、1＝不可用；低分再勾原因。正式擴量後評估是否抽樣，不能讓回饋收集抵銷省下的時間。
- **評分不能代替正確性。**「不用改」不代表沒有錯；仍需獨立抽查，也應記錄人工漏攔。
- **Latency：部分同意。**email 不必追求即時對話的速度，但應區分草稿生成時間、客服操作時間與客戶等待時間。不建議為了「看起來不像 AI」刻意延遲寄送，應先確認 SLA 與客戶期待。
- **分類評估：兩者都要。**離線 eval 用於版本驗收，上線抽樣用於發現真實分布變化。LLM-as-judge 可協助篩選疑似問題，但需先與人工評分校準，重要爭議由人工裁決，不能單獨決定上線。
- **生成錯誤：Agree。**分成事實、完整性、來源、語氣與越權承諾；另區分「草稿內發現」和「已送出」，兩者處置不同。
- **系統 error rate：Agree 改名。**仍需區分以請求為分母的失敗率及以工單為分母的受影響比例，避免一次工單多次重試把數字放大。

### 7.3 測試量與 350–700 件日流量

**Agree：**原答案直接指定 200／300 筆、兩週與 10% 流量，沒有說明如何取得及需要多少客服審核時間。

**Disagree：**不能只因每天 350 件，就認定兩週測 200 筆一定不合理。試點通常只涵蓋部分類別與流量，關鍵是把假設寫出來。

- 例如以一般產品詢問 30%、其中 10% 進試點估算：350 × 30% × 10% ≈ 每天 10.5 件；14 天約 147 件。這只是候選上限，真正符合低風險條件的可能更少。
- 將「離線測試案例數」「線上符合條件的流量」「人工抽查量」分開，不混用合成案例和真實工單證明營運效果。
- 晉級同時滿足觀察期間與有效樣本數；未累積足夠樣本就延長，不因日期到了自動升級。
- 任務成功率不能只抽已結案案件。固定觀察一批進件，期限內仍未解決的也需計入失敗或待處理，另標示尚未成熟的觀察資料。

## 8. Q5：依風險與效益決定 rollback

**你的意思：**先關自動回覆；草稿若仍有價值應保留，並讓客服主管參與決定，不要把所有 AI 輔助一起拿掉。

- **Agree：**原答案由三起事故直接推到停用受影響草稿，條件不夠細。應先區分來源、錯誤類型、影響範圍，以及客服是否有能力有效攔截。
- **Disagree：**不能事先認定草稿完全不需停用。若它持續誘發錯誤承諾、洩露個資，或修改成本高於自行撰寫，應暫停該能力。
